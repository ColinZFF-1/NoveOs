### 4.2 WebSocket 压测脚本

```python
# ws_pressure.py
import asyncio
import websockets
import time
import json

async def ws_client(client_id: int, duration: int):
    uri = "ws://localhost:8000/ws/projects/pressure_test_project"
    async with websockets.connect(uri) as ws:
        start = time.time()
        msg_count = 0
        latencies = []

        while time.time() - start < duration:
            try:
                msg = await asyncio.wait_for(ws.recv(), timeout=10)
                data = json.loads(msg)
                latency = time.time() - float(data.get('timestamp', time.time()))
                latencies.append(latency)
                msg_count += 1
            except asyncio.TimeoutError:
                print(f"Client {client_id}: timeout")
                break

        print(f"Client {client_id}: {msg_count} msgs, avg latency {sum(latencies)/len(latencies)*1000:.1f}ms")

async def main():
    await asyncio.gather(*[ws_client(i, 1800) for i in range(20)])

asyncio.run(main())
```

### 4.3 SQLite 压力脚本

```python
# sqlite_pressure.py
import sqlite3
import time
import threading
from concurrent.futures import ThreadPoolExecutor

def worker(db_path: str, worker_id: int, iterations: int):
    conn = sqlite3.connect(db_path, check_same_thread=False)
    conn.execute("PRAGMA journal_mode = WAL")

    for i in range(iterations):
        start = time.time()
        conn.execute("BEGIN")
        conn.execute(
            "INSERT INTO runtime_logs (project_id, log_id, level, agent, message) VALUES (?, ?, ?, ?, ?)",
            ("test", f"log_{worker_id}_{i}", "info", "System", f"test message {i}")
        )
        conn.execute("COMMIT")
        elapsed = (time.time() - start) * 1000
        if elapsed > 50:
            print(f"Worker {worker_id} iter {i}: {elapsed:.1f}ms")
    conn.close()

# 10 个并发写入
db_path = "~/novel-projects/test/assets/world_state.db"
with ThreadPoolExecutor(max_workers=10) as ex:
    futures = [ex.submit(worker, db_path, i, 1000) for i in range(10)]
    for f in futures:
        f.result()
```

## 6. 容量规划

### 6.1 单机容量模型

| 资源 | 单机规格 | 支撑能力 | 瓶颈 |
|------|---------|---------|------|
| 8C16G | 标准配置 | 3 项目并行（10 Worker） | CPU（LLM 调用等待时 CPU 低，但 SQLite 写入时 CPU 高） |
| 16C32G | 高配 | 6 项目并行（20 Worker） | SQLite 并发写入锁竞争 |
| 32C64G | 顶配 | 10 项目并行 | LLM API QPS 限制（外部瓶颈） |

### 6.2 扩展策略

| 场景 | 策略 | 实施方式 |
|------|------|---------|
| 项目数 > 10 | 水平扩展 | 多机部署，Nginx 负载均衡，SQLite 改为 PostgreSQL |
| 单项目章节 > 500 | 分库 | 每项目独立 SQLite 文件（已支持） |
| LLM API 限流 | 队列削峰 | 增加 Worker 等待时间，降低并发 |
| 前端并发 > 100 | CDN + 静态分离 | Nginx 托管前端，API 独立域名 |

## 7. 瓶颈预判与优化预案

### 7.1 预判瓶颈

| 优先级 | 瓶颈 | 触发条件 | 症状 | 优化方案 |
|--------|------|---------|------|---------|
| P0 | SQLite WAL 文件膨胀 | 连续写入 1000+ 章 | world_state.db-wal > 1GB | 定期 checkpoint，或分卷归档 |
| P0 | LLM API 限流 | 并发 > 2 QPS | 大量 429 错误 | 增加指数退避，降低 Worker 数 |
| P1 | 内存泄漏 | 运行 > 24 小时 | RSS 持续增长不释放 | 检查 PromptBuilder 缓存、日志队列 |
| P1 | 前端 WebSocket 连接数 | 20+ 用户同时在线 | 服务端连接句柄耗尽 | 增加连接池上限，或改用 SSE |
| P2 | 日志查询慢 | runtime_logs > 100 万条 | GET /logs > 2s | 增加索引，或按日期分表 |
| P2 | 情绪曲线渲染 | 240 章全量 | ECharts 卡顿 | 数据采样，只渲染关键点 |

### 7.2 应急预案

```yaml
# 预案 A：SQLite 锁死
触发: busy_timeout 持续触发，写入停滞
动作:
  1. 自动降低并发 Worker 数（10 -> 5）
  2. 发送告警
  3. 如 5 分钟未恢复，自动暂停所有项目
  4. 人工执行 PRAGMA wal_checkpoint(TRUNCATE)

# 预案 B：LLM API 全挂
触发: Circuit Breaker OPEN 持续 10 分钟
动作:
  1. 自动暂停所有流水线
  2. 发送 P0 告警（电话）
  3. 保留队列状态，不丢失任务
  4. 人工切换备用 API Key 或模型

# 预案 C：磁盘满
触发: 磁盘使用率 > 90%
动作:
  1. 自动停止新任务创建
  2. 自动清理 7 天前 debug 日志
  3. 发送告警
  4. 人工扩容或归档旧项目

# 预案 D：单章死循环
触发: 同一章节重试 > 5 次仍 BLOCKING
动作:
  1. 自动标记该章为 error
  2. 跳过该章，继续下一章
  3. 记录详细日志供人工分析
  4. 发送告警
```
